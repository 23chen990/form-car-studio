# 给 Codex 的一次性实施交接（待 Owner 审阅的实现方向）

FORM Owner 已明确希望**首发支持 Style＋Extra＋Color 一次组合生成**，而不是只允许颜色预设。现在不要重复做竞品逆向，也不要重写当前 F12–F17、F23/25 钱包或 F18 Native 的工作。

1. 先阅读本包 `01_PRODUCT_AND_PROMPT_DECISION_ZH.md` 及其研究用 `compose.mjs`、`compose.test.mjs`。对照当前 PR #3 实际 HEAD，确认 `shared/v2/edit-plan.ts`、`server/v2/plans.ts`、`server/v2/presets.ts`、`shared/v2/provider-prompt.ts`、`server/v2/provider-profile.ts`、F13/F14 组件、F32 接线的真实范围和测试依赖。不要假设 2026-10-14 的代码一定仍是最新。
2. 准备**最小受审 S01/S02 能力/请求协议 RFC**，记录兼容现有 schema 的升级路径，新 Style/Extra/Color 的合法 ID、一个 Extra 的选择策略、单次输出计费、组合互斥和优先顺序、历史版本保真、Provider Profile 发布/回滚、安全与不可变 quote。不得把本研究模块直接 import 进生产以绕过守卫，也不应自动修改冻结规格。
3. 获批后在现有系统增量实现：前端一个选择会话，一次组合确认；服务端静态、版本化 Prompt 模块组合；冲突发生在报价**之前**阻止；一个确认只提交一项生成任务。正式结果保存确切 recipe、templateVersion、源版本；不改变历史已扣账单和权限数据。
4. 默认不要添加每次调用的 LLM 提示词重写服务。研究型对照可设计 `deterministic` vs `LLM rewrite`，但必须独立审批预算、成本、错误语义与附加延迟。复杂 Extra 质量验证失败时不要默默用换色替代，却仍收费“宽体已完成”。
5. 至少复用研究脚本覆盖 21 项边界：未知 ID、空结果、同照片同组合稳定、颜色覆写、部分结构允许变化、不能出现“加尾翼又禁止加尾翼”、版本精确、用户源权限、额外 LLM=0、单次输出/幂等、欠费/失败不重复扣费；另补真实 V2 类型合同和 CI。
6. 对当前 Provider 无法证明效果的 Extra 不允许在真实付费目录中开放。质量实验需要另外的照片处理权和额度上限；目前 9 次只是一个待审批快速筛选建议，252 次原有研究计划尚未授权。

范围保护：不合并任何 Draft PR，不修改 main，不部署，不调用收费模型、不执行 StoreKit 真交易、不迁移生产数据；除非已有明确、独立授权。完整执行提案评审所需的静态分析/合同草案，不要因为缺少费用授权就停止可完成的离线部分。交付时列出最小规格修改和可验证测试，不再泛泛输出“建议研究”。
