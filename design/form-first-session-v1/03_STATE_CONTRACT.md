# 状态、适配器与数据契约

## 1. 绝对不能移植的东西

`prototype/model.mjs` 是**模拟器**：它有客户端模拟余额、模拟同意和人工推进任务。它只用来验证页面反应，不能成为生产 auth/wallet/job 实现。
`prototype/flow-policy.mjs` 是纯 UI 决策选择器，可以按当前接口适配；它也不是权限或账本。生产服务器仍验证每次动作。

`contracts.d.ts` 是接口建议，不新建生产接口。现有 `/api/v2` 路由、原生 Apple 回调和数据结构优先；字段对不上时在适配层映射，不让弱模型另造一套服务器。

## 2. 主按钮决策顺序（固定，勿靠组件各自猜）

| 顺序 | 当前条件 | 主动作 | 不得发生 |
|---|---|---|---|
| 1 | 已有活动任务 | 返回该任务 | 再下新单或新扣次 |
| 2 | 没有照片 | 选图 | 创建空项目 |
| 3 | 离线 | 解释并重连 | 丢草稿/伪造请求成功 |
| 4 | 能力/真实供应商未批准 | 浏览示例、说明不可用 | 收费或上传后才说做不了 |
| 5 | 文件本地检查失败 | 换图 | 继续提交不支持格式 |
| 6 | 未登录 | 原生 Apple 登录 | 在云端建立不可靠付费身份 |
| 7 | 同意不存在/过期/处理方改变 | 查看真实处理说明 | 旧同意默认授权新处理方 |
| 8 | 私有资产未准备好 | 明示上传/准备照片 | 无同意传输，或称已生图 |
| 9 | 报价不存在/过期/不匹配草稿 | 刷新报价并展示变化 | 沿用旧基础版本/旧费用 |
| 10 | 余额未知 | 同步余额 | 当成0强推购买，或当成免费 |
| 11 | 余额不足且试用获批并明确eligible | 领取批准权益 | Cookie/重装/换活动无限发次 |
| 12 | 余额不足且商品目录有效 | 真实次数包页面 | 编造价格、默认订阅 |
| 13 | 商品不可用 | 保留选择、稍后重试 | 假支付流程 |
| 14 | 全部准备好 | 明确创建1图、使用1次 | 登录/购买回调直接生成 |

离线时已有任务可以显示本地可用摘要，但状态更新需网络，不能把缓存状态说成当前已完成。

## 3. 保留意图，而不是保留一个“当前页面”字符串

Draft/intent 需要绑定：
`projectId`、`sourceAssetId/sourceVersionId`、`sourceDigest`、`operation`、`styleId/presetVersion`、明确 edits、`draftRevision`。
认证/购买暂时离开时保存 intentId 和可安全持久化的草稿引用；不把原始照片、Keychain token、Apple JWS 放 localStorage。

返回后次序：
1. 当前 actor 是否相同、是否有活动请求/未完成购买；
2. 资产是否仍归属该用户、是否已删除；
3. 草稿是否被另一设备修改；
4. 模型能力/数据同意是否仍适用；
5. 报价是否仍有效、余额是否已确认；
6. 展示当前摘要，等待明确创建。

任何失败都返回具体恢复动作。不要 silent fallback 到最新版本，不要用陌生示例填空，不要丢失已付余额。

## 4. 一次意图与重复请求

`submissionId` 在发请求前持久化，网络超时后先查询该ID对应的任务，必要时同ID重放。
同 key 相同冻结语义返回原任务，不同语义409。
最终创建按钮按下后视觉上进入提交中；同时服务器还要幂等。单纯前端disable不构成防重保证。
成功只有一个正式结果版本；失败原请求保留。用户明确确认重试才创建新逻辑请求，并关联原失败记录。

## 5. 等待时序

正常：`preparing/uploading → confirming → submitting → queued → processing → succeeded`。
不确定：`processing → uncertain → succeeded/failed`，具体根据服务器支持的核对策略。
取消：`queued → cancelled`。已提交上游后只允许离开；不得宣称取消上游肯定免成本。
前台轮询：初始2秒，30秒后5秒，单任务至多一个在途请求；隐藏页暂停轮询，返回后刷新。它不是模型速度承诺。
禁止将上述时间当作自动退款/自动重试或伪造进度百分比的依据。

上传有实际进度数据才显示上传百分比；生成没有可靠数据就只显示状态。
成功已保存但图片下载失败：重取资产，不新生成；服务端已失败但返还未确认：提示核对余额，不写“已退”。

## 6. 购买状态（独立于生图）

`catalog_loading → selectable → system_purchase → pending / cancelled / failed / verification → credited / already_credited / verification_unknown`。
Pending 和 verification_unknown 都不再次卖同一需求。重启恢复未完成交易并继续核对。
用户取消买包：回同一Review，零新任务。
确认到账：先刷新余额/报价回Review，仍然零新任务；再按明确创建按钮才提交。
恢复消耗型余额靠本账号账本，不重放所有历史内购再发一遍。

## 7. 输出与保存

ResultView 的信息来自已授权持久版本，不从 prompt target 伪造“已按要求修改”。
`desiredRecipe` 可显示“requested”，`observedRecipe` 只显示真正验证过的部分；未知保持未知。
收藏是 metadata，保存相册是系统操作，分享是系统sheet；三个事件的成功条件分别确认。
最小导出为常见PNG/JPEG，保持原图比例；portrait卡片周围留白，而不是硬裁车辆。原型导出的SVG只是原创示意图，不是未来用户照片文件格式建议。

## 8. 生产与原型差异清单

| 原型行为 | 生产替换 |
|---|---|
| 模拟账号按钮 | 官方 Apple 组件 + 服务端验证；真实token在Keychain |
| 一项“理解演示”复选框 | 权利、上传、AI处理的真实披露及版本化许可 |
| Price from App Store 占位词可模拟买包 | StoreKit已加载并与后端目录一致才可购买 |
| 客户端balance数组 | 后端账本摘要，未知显式处理 |
| 人工完成/约6秒示意流程 | 服务端任务事件，无模拟延迟 |
| sessionStorage保存示例JSON | 私有服务端作品，受控本地cache；不存敏感原件 |
| 原创SVG示例 | 已授权真实案例/用户图片，能力验证后使用 |
| 页面反馈内存记录 | 身份验证后的feedback API，限长、脱敏、审批独立 |

每项替换必须有适配器测试。不得把“原型能点通”标记为生产接口联调完成。
