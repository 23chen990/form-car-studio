# 讨论整理与静态报告的证据边界

## 产品目标不变

FORM 面向普通车主，以较低成本做出有人愿意使用、付费的汽车外观创作产品，不追求行业头部。首要验收是“看完之后是否真的想选自己的车照片”，不是页面数量、功能数量或测试总数。

前轮反思保留：流程完整不等于有吸引力；示意车和抽象风格名不足以支持上传动机；普通车主更容易理解具体变化，而非 AI 参数。真实、授权、能代表 FORM 实际能力的案例仍是缺口，不得用概念素材掩盖。

对“灵感相册”的建议加上限制：相册只服务于上传前发现方向，不扩展社区、信息流推荐或大型模板商城。补充 GARAGE 截图进一步提示，选图后应迅速进入以自己的车为中心的工作区，详见 03。

## 静态报告实际支持的事实

来源 `STATIC01`：用户上传的 `mody-static-report.txt`，记录安装包版本 3.1.440、构建号 2、最低系统版本 18.0、包标识 com.cartuning.appitech。这些是该安装包记录，不是当前商店或录屏版本的再次认证。

| 检查发现 | 可以说 | 不可以说 |
|---|---|---|
| Flutter、App.framework/flutter_assets | 包内存在 Flutter 客户端相关组件 | 应照搬技术栈，或其界面因此更好 |
| RevenueCat、RevenueCatUI、purchases_flutter | 包内存在内购相关组件 | 仅凭 SDK 判定订阅周期、价格、付费时机、收入 |
| Firebase Remote Config、ABTesting | 包内存在远程配置/实验相关组件 | 已证明具体实验、胜出方案或高转化率 |
| Adjust、跟踪授权相关组件 | 包内存在归因/授权相关组件 | 已证明投放规模、获客成本或商业成功 |
| 图片选择、裁剪、压缩、相册保存相关组件 | 存在相应客户端集成线索 | 所有功能均已启用、图片上传已成功 |
| video_player 等组件 | 存在视频播放相关线索 | 已证明视频生成供应商、速度或稳定性 |

保留的推断：Mody 的技术组成体现了覆盖商业化、配置及媒体能力的集成范围。但“重视运营”“持续实验”仍是推断；不以此作为 FORM 引入整套 SDK 的依据。

## REA 日志并非分析结果

来源 `REA01`：`mody-analysis.txt` 报告 Hopper bridge 启动等待超时，阶段为 startup、provider_state 为 not_started，并报告 cleanup_incomplete。没有成功输出可核验的应用内部逻辑或提示词。

不将失败归因于竞品反分析技术、加密强度或服务器架构；日志没有提供这些证据。本次不重试 REA，不启动 Hopper，不做许可证或保护机制绕过。

## 录屏带来的增量

现在不必再只说“可能有订阅”：视频约 83–90 秒可见订阅营销页及 App Store 年订阅确认面板。但是只证明这段录屏中的一次展示，不能推出所有地区、账户或版本的统一政策，更没有购买成功证据。

现在也能观察到主页面的 Style Builder/Custom Edit 双入口及风格、额外、颜色三个配置入口；这支持研究它怎样降低表达成本，不支持推断模型实际遵守每个选项。

## 对上轮讨论的修正

1. 不把 SDK 清单称为完整的竞品体验分析。
2. 不以“漂亮”“高级”“高星技能”替代案例质量及上传意愿证据。
3. 上轮谈到的网络参考车图不视为同车前后对比，也不转存为产品素材。
4. 此前的“先产生期待再付费”保留为 FORM 设计建议；录屏显示 Mody 更早就出现疑似付费壳，不能声称竞品已验证了这条建议。
5. Skills 用于检查视觉层级、状态和移动端细节；不重新发布上轮未经本次核验的星标数，也不声称安装或 CLI 已执行。
